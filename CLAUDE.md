# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ScoreChat is a symbolic-score RAG system for classical piano music in Humdrum (`.krn`) format. The design principle: the raw score and deterministic `music21`-derived analysis are the source of musical truth; retrieval/embeddings and the LLM only locate and explain evidence-backed passages — they never invent or override musical facts. Keep this separation in mind for any change: analytical claims must trace back to `score_measures`/`measure_analyses`/`span_analyses`, not to LLM output.

## Commands

Setup (uses `uv`, per memory prefer `uv pip install` over bare `pip`):
```bash
uv venv
source .venv/bin/activate
uv pip install -e ".[dev]"
docker compose up -d          # postgres + pgvector, schema auto-applied from db/schema.sql on first init
```

If the DB predates a schema change, apply migrations manually (not auto-applied on existing volumes):
```bash
psql "$DATABASE_URL" -f db/migrations/001_symbolic_layers.sql
psql "$DATABASE_URL" -f db/migrations/002_span_analysis.sql
psql "$DATABASE_URL" -f db/migrations/003_notated_sections.sql
psql "$DATABASE_URL" -f db/migrations/004_measure_roles.sql
psql "$DATABASE_URL" -f db/migrations/005_drop_omr_columns.sql
```

Ingestion pipeline:
```bash
python download_beethoven_piano_sonatas.py --sonata 32   # fetch .krn from craigsapp/beethoven-piano-sonatas
python ingest_scores.py                                  # parse -> analyze -> MEI -> embed -> store
python ingest_scores.py --symbolic-only                  # skip MEI/embeddings, just rebuild symbolic layers
python build_sections.py                                 # record notated section structure (run before relations)
python build_relations.py                                # propose span_relations from stored data (no .krn needed)
python build_relations.py --work-id 197 --dry-run        # tune thresholds without writing
python renumber_measures.py                              # re-derive which measures are bars (DB-only)
python build_harmony.py                                  # re-key and re-chord from stored data (DB-only)
python evaluate_form.py --verbose                        # score the pipeline against known answers
```

Ask a question (tool-calling; needs `CHAT_PROVIDER` and its key):
```bash
python ask.py "where is the recapitulation in the Moonlight finale, and what supports it?"
python ask.py "compare mm. 1-8 with mm. 103-110 of op 27 no 2 iii" --no-trace
```

Run the app:
```bash
python server.py                    # API + static HTML/JS client at http://localhost:8000
streamlit run scorechat_app.py      # alternative Streamlit chat UI
```

Tests:
```bash
pytest                              # full suite
pytest tests/test_analyzer.py -k test_detect_texture_with_music21   # single test
```
Some `test_analyzer.py` cases are skipped unless `tests/fixtures/sample.musicxml` exists.

## Architecture

Ingestion pipeline: Humdrum `.krn` → `music21` parse → canonical measure encoding → versioned symbolic analysis → optional retrieval segments/embeddings → MEI (via Verovio) for browser rendering. See `architecture.png` (source: `docs/architecture.svg`; re-render with cairosvg after editing) and `README.md`'s "Symbolic Score Data Model" section for the full table-by-table breakdown (`score_sources`, `score_measures`, `measure_analyses`, `analysis_runs`, `span_analyses`, `span_relations`).

Key modules:
- `analysis/analyzer.py` — score loading plus all `music21`-based feature extraction: measure encoding, texture candidates, and `build_span_candidates` (span analysis at meter changes, notated directions, structural barlines — does not infer form/theme labels). Harmony is delegated to `analysis/harmony.py` as a second pass over the finished canonical layer.
  **Always load scores through `load_score()`, never `converter.parse()` directly.** music21's Humdrum reader silently truncates scores containing nested spine splits (Op. 14 No. 1/i parsed 12 of its 162 measures), so `load_score` checks the parse against the `=N` barlines the source notates and falls back to Verovio's humlib importer via MEI when it comes up short — 4 of the 103 movements need this. That MEI in turn carries key/meter in elements music21's MEI reader ignores, so `humdrum_signatures()` reads them from the raw `.krn` and they are stamped onto the opening measure; without that the recovered scores lose the key-signature anchor entirely. `ingest_scores.py` re-checks the same barline count and refuses to store a short parse, because a truncated score looks perfectly healthy downstream.
- `analysis/harmony.py` — key trajectory and chord/Roman-numeral analysis. A *pure function of `score_measures.symbolic_data`*, not of a music21 parse, so a harmonic pass is reproducible from the DB alone and re-runnable without the source `.krn` — preserve that seam. Key estimation is windowed + Viterbi-smoothed and anchored to notated evidence. **The strongest anchor is the key the score declares** (`*f:`) — all 103 movements state one, and `analysis/humdrum.py` reads it, so `global_key` is now engraved rather than estimated. It outranks the cadential guess, which misread eight movements: six genuinely (usually as the relative major — Op. 90/i as G major, Op. 101/iii as C major) and two only in spelling, where the declaration also wins because `D- major` is what the page says and `PITCH_NAMES` has no name for it. Failing a declaration, the fallbacks remain the staff key signature (`SIGNATURE_BONUS`) and the bass of the final sounding measure (`HOME_KEY_BONUS`), which is what separates a key from its relative. Note the declaration anchors the *trajectory* and fixes the home key; it does nothing for the estimator's stickiness, so 22 of 103 movements still report a single key region. Chords are fitted to beat-sized windows by template matching, so output tracks harmonic rhythm rather than note onsets, and spans below `MIN_CHORD_CONFIDENCE` are deliberately left unlabelled. Two rules there are load-bearing and each has a ground-truth test: a window with fewer than `MIN_DISTINCT_PITCH_CLASSES` cannot determine a triad and borrows pitch content from the *narrowest* surrounding context that can (an arpeggiated measure is one chord, not one per note); and the bass is the lowest *sustained* pitch in the window (`BASS_MIN_DURATION_SHARE`), which is neither the lowest note to occur — a figure dipping below the bass would invert the chord — nor the note on the beat, since an accompaniment often enters under a held melody. Reported `correlation` and `confidence` deliberately exclude the bonus/bass weightings used to *select* an answer — keep selection and reporting separate, since these values reach the LLM as evidence. Tuning constants are pinned by ground-truth tests in `tests/test_harmony.py`; re-run those after touching them. `build_harmony.py` re-runs the whole pass from the database in about 18 seconds — the seam was designed for this from the start but had no CLI, so the only route to a new harmonic analysis used to be a full re-ingest through music21.
- `analysis/humdrum.py` — reading the `.krn` directly, spine by spine, for the facts music21 does not carry faithfully. **It cannot be done by column index**: `*^` splits a spine and shifts every column to its right, a run of `*v` merges them back, and all 103 movements do it (2,396 splits, 4,772 joins), so the third column is `**dynam` only until the first divided staff — which is how kern note tokens ended up stored as dynamics. `spine_layout()` tracks this and is validated by an invariant that holds across all 175,279 lines of the corpus: the layout must have exactly as many spines as the line has tokens. `declared_key()` reads the `*f:` every movement states (see the harmony note below), and `meter_changes()` the `*M` records: music21 loses meter changes in 3 of the 103 movements — Op. 111/ii is written 9/16, 6/16, 12/32, 9/16 and only the opening 9/16 survived, Op. 110/iii loses three of its nine, Op. 53/iii its closing 2/2. **A stale bar length does not merely mislabel the metre**: `analysis/numbering.py` measures every bar against it, so whole bars in a faster meter read as incomplete and were classified as upbeats. The meter is now stamped on every measure rather than only where it changes, so no consumer has to forward-fill.
- `analysis/numbering.py` — which measures are bars and which are merely part of the score. A pure function of `(index, importer's number, sounding duration, bar length)`, so it runs at ingest and again over a stored corpus. See the measure-numbering contract below; the rule and its meter-dependence are pinned by `tests/test_numbering.py`.
- `analysis/sections.py` — notated section structure from Humdrum expansion records (`*>[A,A,B]` plus `*>A` labels), stored as spans with `span_type='section'` and confidence 1.0 because it is engraved, not estimated. `music21` discards these records entirely, so they reach us only from `score_sources.raw_content`. This is the strongest form evidence the corpus carries: a repeat spanning much of a movement is the clearest indicator of sonata form (62% of first movements have one covering ≥30% of the movement, against 16% of second movements and none of the fourth), and *which* section repeats characterises the movement — both halves is the Classical norm, a repeated second section with an unrepeated first is Beethoven inverting it (Op. 57/iii), a short unrepeated section first is usually a slow introduction outside the form (Op. 111/i), and no expansion record at all means no repeat was notated (Op. 57/i). A `*>B` record is written immediately *after* the barline that opens section B, so that barline is B's first measure and not A's last — Op. 111 marks `=19!|:` then `*>B` and its Allegro is bar 19; reading it the other way dates every boundary in the corpus one bar late. Section ends are derived from the next section's start rather than collected, so a section cannot claim the barline that opens its successor. The parser records the scheme and never names a section an exposition or a development; 42 of 103 movements notate nothing.
- `analysis/span_relations.py` — symbolic comparison between spans, and the relations pass (`build_span_relations`, driven by `build_relations.py`). Depends only on the database, never on the source `.krn`, so it is re-runnable and re-tunable without re-ingesting. Three things carry the quality of the output and each has tests: reference spans come from a **uniform tiling** (`REFERENCE_WINDOW_LENGTHS`) as well as from `span_analyses`, because boundary candidates break at every notated direction and so are not a thematic index (two thirds are 1–2 measures, while a movement with no directions collapses to one span — relying on them alone left a quarter of the corpus with no relations); overlapping matches of one return collapse to the strongest (`_select_distinct_matches`); and relations sharing a target-minus-source *offset* with touching source ranges merge into one (`_merge_by_offset`), taking the weakest part's confidence, while ranges separated by a gap stay apart since that gap was never compared. `detect_intro_end_index` reads the notated sections rather than scanning for a repeat sign: a short unrepeated first section followed by a repeated one is an introduction (`MAX_INTRO_SHARE`), and a section scheme that describes no introduction is evidence there is none — which is why a movement notating sections never falls through to the tempo-change guess, and why the tempo guess itself is bounded to the opening. `corroborate_key_match` compares the windowed `local_key`, not `global_key` — the latter is now one value per movement and would corroborate everything. `check_varies` compares interval sequences and is therefore transposition-invariant by design, so `transposition_interval()` measures the offset separately and records it as `transposed_semitones` with a `transposition_consistency`; that is what separates a theme returning at pitch from a second group brought home from another key (0 vs 5 semitones), and a low consistency means no single interval explains the pair, so the value must not be read as one.
- `evaluation/`, `evaluate_form.py` — the eval set: ten movements whose form is known independently, scored against what the pipeline has actually stored. Every other check in this repo asks whether a function does what it was written to do; this one asks whether the pipeline finds the musical facts a reader would ask about. Two things about `evaluation/ground_truth.json` are load-bearing. It records the published `recapitulation` bar *and* the `literal_return` bar separately, because they are not the same thing — the Waldstein's recapitulation is at m. 156 but note-for-note correspondence with m. 3 does not resume until m. 160, and a symbolic matcher can only ever find the second; scoring against the published bar would mark a correct finding wrong. And every `literal_return` carries a `verified` confidence measured in the corpus rather than recalled, with a test asserting that a claimed return actually scores as one — three entries record a null return, which is a real negative the harness requires the pipeline to *also* return nothing for, so the metric cannot be improved by lowering a threshold. `return_recall` (is the return proposed at all) is scored apart from `return` (is it ranked first), since nothing yet does the ranking.
- `db/models.py`, `db/schema.sql`, `db/store.py`, `db/session.py` — SQLAlchemy models, raw schema (source of truth for the DB, applied via docker-compose init and `db/migrations/*.sql` for existing DBs), persistence/query helpers (e.g. `get_measure_evidence`).
- `pipeline/retrieval.py` — pgvector cosine similarity search over `score_segments`/text sources.
- `pipeline/embedder.py` — embedding generation via the configured `EMBEDDING_PROVIDER`.
- `pipeline/providers.py` — env-driven selection of chat/embedding backends (`CHAT_PROVIDER`/`EMBEDDING_PROVIDER`: openai/anthropic/ollama/gemini) via LangChain, so no code is hardcoded to OpenAI. Anthropic has no embeddings API. Switching `EMBEDDING_PROVIDER` to a model with a different output dimension than the schema's `vector(1536)` columns requires a schema migration + full re-embedding.
- `pipeline/analysis_api.py` — the questions ScoreChat can answer, as plain functions (`resolve_work`, `describe_span`, `find_recurrences`, `compare_spans`, `get_key_plan`, `locate_in_form`). Kept apart from the tool bindings so the answers are testable without a model in the loop. Two conventions hold throughout and both have tests: **printed bar numbers in and out**, with ranges resolved through `measure_belongs_to` so a range opening on a pickup still reports itself as the bar it leads into; and **absence is an answer** — a movement notating no sections, a range with no recurrences, a comparison below threshold each return an empty result with a `note` saying so, never a guess, because an empty result with no explanation is the one thing a model will fill in for itself. `resolve_work` returns `resolved: None` when several movements match equally rather than picking one, since a wrong work puts every later answer in the wrong music; an opus-and-number is matched as a unit (`Op. 27 No. 2`, not the loose tokens "27" and "2", which match Op. 27 No. 1 just as well), nicknames are matched with accents folded, and "last movement" resolves only once the field is one sonata.
- `pipeline/tools.py` — that API bound as LangChain tools, plus the call loop (`answer()`), driven by `ask.py` and served at `/api/ask`. Tool calling rather than retrieval because neither headline question is a retrieval problem: in "describe mm. x–y" the measures are *given*, and "find recurring material" is an edge in `span_relations` that vector search over prose summaries cannot reach. The returned `trace` is the citation — a claim with no supporting call in it is one to distrust. A tool that raises returns its error to the model to recover from rather than aborting the answer, and a model that never stops calling tools is cut off after `MAX_TOOL_ITERATIONS` and asked to answer from what it has. `_text()` flattens provider content blocks; Gemini attaches a signature block to every reply, and rendering the list puts a base64 blob in front of the user.
- `pipeline/chat.py` — RAG chain (prompt | chat model | parser). Builds LLM context from retrieved segments, capping unique measures per response (`MAX_SYMBOLIC_CONTEXT_MEASURES`) and injecting `symbolic_evidence` JSON per measure so answers are grounded and measure-cited.
- `pipeline/mei_converter.py` — MusicXML → MEI via Verovio bindings, for exact SVG notation rendering in-browser. `mei_to_svg` takes **printed** measure numbers and translates them through `measure_ordinals()`; see the measure numbering note below.
- `frontend/index.html`, `frontend/score_viewer.html` — HTML/JS client; renders notation slices client-side via Verovio WASM.
- `server.py` — API + static file server backing the HTML/JS client.
- `scorechat_app.py` — alternate Streamlit-based chat client.

Measure numbering — two numbering schemes exist and confusing them fails silently (the viewer just shows neighbouring bars):
- **Printed/engraved** (`score_measures.measure_number`) — what a performer reads, what a user types, and what the LLM must cite. Bar 1 is the first *complete* measure. **NULL when the measure is not a bar**, which is a normal condition rather than a parse failure: an anacrusis, the upbeat written after a repeat barline, a deliberately unbarred cadenza. `measure_role` (`bar`/`anacrusis`/`upbeat`/`unbarred`/`empty`) says which, and `measure_belongs_to` gives the printed bar it is *reported* against — for a pickup, the bar it leads into. A database constraint keeps the two columns consistent: a row has a number if and only if its role is `bar`.
- **Internal** (`score_measures.measure_index`) — 0-based position including every measure, bar or not. All span/relation work (`span_analyses.measure_start_index`, `analysis/span_relations.py`) keys on this.

  **Always resolve a user-facing range through `measure_belongs_to`, never `measure_number`.** `WorkFeatures.bar_of()` and `analysis/numbering.py`'s `resolve_range()` do this; `get_measure_evidence` selects on it, so asking for mm. 229–247 returns the upbeat into 229 along with it, and `mei_to_svg` backs up over the same pickup via `pickup_ordinals()` so the rendering matches the citation. `opens_on_pickup` is recorded alongside, because "from the upbeat to m. 229" is what a musician says and what distinguishes that range from one starting on the downbeat.

  This replaced a sentinel `0`, which meant the importer's refusal to number a measure was stored as something that read as a bar number and got printed as one: the pipeline located Op. 2 No. 2/i's recapitulation correctly and reported it as *mm. 0–247*. 134 rows are affected across the corpus — 47 anacruses, 56 upbeats, 22 unbarred, 9 empty artefacts — and only the 9 are junk. The 22 remaining unbarred concentrate in two movements (Op. 2 No. 3/i and Op. 31 No. 1/ii), both genuinely unbarred cadenza writing. music21 is right to decline to number the rest; a performer does not call them bars either.

  **Bar numbers are derived, not copied.** Every source numbers its barlines exactly 1..N — no gaps, no repeats, checked over all 103 — so the k-th bar is bar k, and `_renumber()` assigns that. music21's own numbering duplicates and runs backwards in 3 movements (Op. 10 No. 3/i claimed 347 bars against the source's 344, numbering the anacrusis and two repeat-upbeats the same as the bars after them), and copying it meant the notation viewer and the chat cited different bars. A number the importer *contradicts elsewhere* is not evidence, so a duplicated number on a measure that is arithmetically a pickup is overridden; an uncontradicted short measure — a legitimately short final bar — is left alone. Stored numbering now agrees with the source in 103 of 103.

  On the viewer side, `measure_ordinals()` accounts for `<multiRest num="k">`: two bars of rest are engraved as one measure, so Op. 110/ii's MEI has no measure numbered 38 and a request for it used to render a neighbour silently. Two bars in two movements remain unaddressable (degenerate measures at a tempo change, Op. 27 No. 1/iv m. 266 and Op. 31 No. 3/iii m. 20); `tests/test_measure_numbering.py` pins that count so it cannot quietly grow.

  `analysis/numbering.py` decides this arithmetically rather than from barline symbols: an upbeat is a partial measure that, with the short measure before it, makes exactly one bar. That makes it depend on two things being right, and both were wrong. **A measure is as long as its span** — `db.store.measure_span()`, `max(offset + duration)` — and not the sum of its event durations, which counts simultaneous voices twice: a divided staff in Op. 111's Arietta summed to 3.0 in a bar 1.5 long, and 16 complete bars across the corpus were classified as unbarred because of it. **And the test needs the meter** — two 2.0-beat measures are a split bar in 2/2 and two whole bars in 2/4 — so the bar length is passed per measure, from music21 during ingest and from the forward-filled `time_signature` in `get_measure_shapes()` afterwards. `renumber_measures.py` applies the pass to a stored corpus without re-ingesting it, the same DB-only seam as `build_sections.py`.

**Open question — alternate endings.** All 103 sources number strictly sequentially: no bar number is ever repeated and none is skipped (verified across the corpus). Printed editions often do otherwise, numbering a first and second ending as 69 and 69b/69bis so both count as bar 69. If the edition a reader has in hand does that, our numbers run ahead of theirs from the second ending onward. **36 of the 103 movements have alternate endings**, and the accumulated drift reaches 10 bars (Op. 57/iii), 9 (Op. 111/ii) and 8 (Op. 27 No. 1/ii) by the end of the movement. 102 of the 103 encodings name the same reference edition — **Durand 1915, Paul Dukas ed.**, a performing edition rather than an urtext — and `analysis/humdrum.py`'s `reference_edition()` reads it, with `resolve_work` returning it so an answer can say which edition its bar numbers are from. Henle/Wallner, the urtext a reader is most likely to hold, does use the shared-number convention. The `**dynam` spine is Dukas's editorial dynamics too, not Beethoven's. Supporting the printed convention would mean a `measure_suffix` column ('b') alongside `measure_number` and re-deriving numbers across every alternate ending — a real change, not a repair. Do not assume either convention is the user's.

Verovio agrees with printed numbering in its MEI (`@n` absent on a pickup), but its `select({"measureRange": ...})` counts **ordinal positions from 1**, in which the pickup *is* position 1 — so printed bar N is ordinal N+1 wherever an anacrusis exists. Translate via `measure_ordinals()` (Python) or `measureInfo()` (`frontend/score_viewer.html`); `frontend/index.html` sidesteps it by resolving `@n` to `xml:id` and navigating with `getPageWithElement`. Note the older `select` *option* is silently unsupported in Verovio 6 and renders the whole movement — use the `select()` **method**, with a dict, before `loadData`.

Span/relation review lifecycle: `span_analyses` and `span_relations` rows carry a status of `proposed`, `accepted`, or `rejected`. Every row the pipeline creates is `proposed` — there is no UI yet for accept/reject. `span_relations` now carries `repeats`/`varies` proposals from the pass above; the other relation types (`inverts`, `diminishes`, `augments`, `changes_meter_from`, `contrasts_with`) still have no analyser. Relations are evidence, not form labels: a target range with no span of its own gets one created as a `candidate`, never as a `theme` or `variation`, and `returns_in_same_key` is recorded alongside the confidence rather than folded into it, because distinguishing a tonic recapitulation from a transposed restatement is exactly what downstream form analysis needs.

## Open work

In the order worth taking it. The first two change the shape of the project; the rest are analysis quality.

1. **Point the web client at `/api/ask`.** Two paths reach the corpus and they are not equivalent. Tool calling (`ask.py`, `/api/ask`) reads stored analysis directly and touches no embeddings; retrieval (`/api/chat`, `scorechat_app.py`, the viewer's chat box) does a pgvector search over `score_segments`. The working path is CLI-only and the web client still uses the other. Resolving this makes the good system the visible one and turns the embedding layer into a deliberate choice rather than inertia.

2. **Then decide whether the vector layer stays at all.** Only `score_segments.summary_text` is embedded — 4,519 prose summaries of measure windows. The score itself is stored exactly as JSONB and queried as data, never searched by similarity. Neither headline question is a retrieval problem: in "describe mm. x–y" the measures are *given*, and "find recurring material" is an edge in `span_relations` that a vector search over prose cannot reach. Dropping it removes `EMBEDDING_PROVIDER`, the `vector(1536)` schema lock, and the re-embedding cost of ever changing provider. See [[scorechat-embedding-layer]] in memory.

3. **The variation blind spot** — the largest remaining hole in the graph. Six movements have no relations at all (Op. 2 No. 1/ii, Op. 27 No. 1/iii, Op. 53/ii, Op. 101/iii, Op. 110/iii, Op. 111/ii), and they are not oddities: `_worth_comparing` divides by the longer event sequence, so a theme (55 events) against its variation (120) caps at 0.73 under a 0.75 threshold and is pruned before a single pitch is compared. Diminution is mathematically excluded. Three axes were probed and none is a cheap fix: loosening the bound does not help (`varies` is 0.00 anyway), per-bar pitch content does not discriminate (an unrelated stretch scored 0.42 against the theme while variation 2 scored 0.34), and harmonic *progression* is the only axis with real signal (var1 0.34, var3 0.20, var4 0.21 against unrelated 0.07) but variation 2 at 0.10 barely clears it. Chord coverage is good (89–100% labelled), so the data is there; a fix needs alignment plus comparing chord *function* rather than exact figures, which is what `diminishes`/`augments` were reserved for.

4. **Test debt.** `tests/test_analysis_api.py::test_no_recurrence_is_reported_as_none_found_not_as_no_answer` now *skips* — its tolerance guard means the Op. 57/i honest-negative case, the most important one on the test page, covers nothing. `analyze_harmony` branches on `isinstance(item, dict)` in six places and the dict path — what `build_harmony.py` actually uses — has no test. And `_load` in `tests/test_harmony.py` re-parses through music21 on every call, which is roughly 50 of the suite's 60 seconds.

5. **Key estimation is sticky.** 22 of 103 movements report a single key region; the Moonlight finale misses its g# minor second group. `KEY_CHANGE_PENALTY`. The declared key fixed the *home* key, not this.

6. **Nothing ranks recapitulation candidates** — the one eval failure. The Pathétique's return at m. 197 is proposed but a coda return at m. 301 outranks it. `return_recall` is 10/10 while `return` is 9/10 precisely because locating and ranking are different jobs.

Two facts to carry into any of this. Bar numbers follow **Durand 1915 (Paul Dukas)**, the edition the encodings transcribe, and diverge from a Henle-style urtext in the 36 movements with alternate endings — drift equals the sum of the first endings' lengths, confirmed exactly on three movements. And for the same reason the `**dynam` spine is **Dukas's editorial dynamics, not Beethoven's**, which matters more for any claim about dynamics than the numbering does for bar citations.

## Environment

Copy `.env.example` to `.env`. Required: `OPENAI_API_KEY` (default provider), `DATABASE_URL` (matches `docker-compose.yml` defaults for local dev). Optional provider keys (`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `OLLAMA_BASE_URL`) only needed if `CHAT_PROVIDER`/`EMBEDDING_PROVIDER` are switched — install the matching extra first, e.g. `uv pip install -e ".[anthropic]"`.
